# Аудиоверсия книги — описание проекта

**Проект:** `audiobook` — локальный пайплайн синтеза аудиокниги с клонированием голоса автора
**Статус:** каркас окружения готов, модули синтеза не реализованы
**Дата версии:** 15 сентября 2026 (ред. 2)

---

## 1. Цель

Получить аудиоверсию электронной книги, озвученную голосом автора, без облачных сервисов и без оплаты за символы. Синтез выполняется локально, референс голоса и текст рукописи не покидают машину.

Аудиоверсия — не самостоятельный продукт, а расширение уже существующего входного продукта воронки. Отсюда требование к качеству: слушатель не должен опознать синтез. Если опознаёт — проект не достиг цели, даже если технически отработал.

## 2. Ограничения

| Ограничение | Следствие |
|---|---|
| Прод-машина: Ryzen 7, 32 ГБ ОЗУ, Radeon RX 580 8 ГБ | **GPU не участвует.** AMD выбросила Polaris/GCN4 из ROCm в v5.x, DirectML заброшен с сентября 2024. Работающий путь на RX 580 — только Vulkan + ggml (`llama.cpp`, `stable-diffusion.cpp`), TTS туда не портирован. Весь синтез — CPU. |
| Разработка на Mac (Apple Silicon), прод на Windows | Два разных torch, два способа старта процессов, разные кодировки консоли. Переносимость закладывается с первой строки, а не чинится после переезда. |
| Книга — платный продукт | Лицензия модели имеет значение: XTTS-v2 (CPML) и F5-TTS (CC-BY-NC) — некоммерческие. |
| Голос принадлежит автору | Требуется письменное согласие на клонирование с указанием сфер использования. |
| Рукопись содержит невербальные блоки | Стрелочные цепочки, схемы, многострочные алгоритмы, таблицы, оглавление, библиография. Текст, который читается глазами, не равен тексту, который читается вслух. См. §5.1. |

## 3. Архитектурные решения

1. **Разработка и прод — один код, разные платформы.** Никаких «а на Windows я допишу». Переносимость проверяется автоматически.
2. **Всё тяжёлое — внутри папки проекта.** Веса моделей, ffmpeg, референс лежат в `models/`, `bin/`, `ref/`, а не в домашнем кэше. Переезд = копирование папки.
3. **Идемпотентность.** Рендер займёт десятки часов и упадёт. Каждый чанк кешируется по `sha1(текст + конфиг + латенты референса)`; перезапуск досчитывает только недостающее.
4. **Автоматический контроль качества.** Синтез иногда глотает слова. На 7 часах руками это не найти — сверка ASR-транскрипта с исходником обязательна.
5. **Правится текст, а не аудио.** Файлы с ударениями и карта чтения блоков — единственные человеческие артефакты, они в git. Аудио всегда пересобирается из них.
6. **Конфиг определяет звук.** Референс, seed, модель, паузы — в `config.yaml`. Он в git, он входит в хеш чанка. Через полгода результат воспроизводим.
7. **Решения об экономике принимаются на прод-железе.** Замеры на Mac — проверка работоспособности, не основание для выбора «локально или аренда». См. §8.

## 4. Стек

**Текстовый слой** (главное узкое место русского синтеза):
- RUNorm — числа прописью, аббревиатуры, акронимы, кириллизация.
- RUAccent или silero-stress — ударения и омографы. RUAccent размечает ~98% многосложных слов; silero-stress знает ~4 млн словоформ и ~2 тыс. омографов, легче по зависимостям.
- Собственный словарь исключений: имена, термины метода, названия глав.
- Карта чтения невербальных блоков (`read_rules.yaml`) — см. §5.1.

**Синтез:**
- XTTS-v2 (community-форк `coqui-tts`) — самая лёгкая для CPU модель с клонированием, русский поддержан, референс от 6 секунд. **Лицензия CPML — только пилот.**
- Chatterbox Multilingual v3 (Resemble AI, MIT, 23 языка, встроенный вотермарк) или Qwen3-TTS (Apache 2.0, клон от 3 секунд) — для коммерческой версии. Меняется один модуль, пайплайн не меняется.

**QC:** faster-whisper (CTranslate2, int8, CPU) — ставится pip'ом, одинаково работает на Mac и Windows. Сборка whisper.cpp с Vulkan под RX 580 — необязательный апгрейд позже.

**Сборка и мастеринг:** ffmpeg (`loudnorm`, highpass, тримминг тишины, конкатенация, `.m4b` с главами и метаданными).

**Инфраструктура:** Python 3.11, `uv` + lock-файл, pytest, GitHub Actions.

## 5. Пайплайн

```
рукопись
 1. extract_blocks.py        → chNN.blocks.json
 1.5 read_rules.yaml         → chNN.txt            ← КАРТА ЧТЕНИЯ БЛОКОВ, в git
 2. RUNorm + словарь         → chNN.norm.txt
 3. RUAccent / silero-stress → chNN.acc.txt        ← ВЫЧИТКА ЧЕЛОВЕКОМ, в git
 4. chunker                  → chNN.chunks.jsonl
 5. synth (кеш по хешу)      → cache/<sha1>.wav
 6. qc (faster-whisper, CER) → отчёт, очередь переозвучки
 7. assemble (тримминг+паузы)→ chNN.wav
 8. master (ffmpeg)          → chNN.mp3 + book.m4b
```

### 5.1 Невербальные блоки — шаг 1.5

Шаг 1 отдаёт блоки с типами (`chain`, `flow`, `stack`, таблица, заголовок, абзац). Прямой прогон их в TTS даст чтение символов вслух: «стрелка вправо», «двоеточие», номера страниц из оглавления.

Каждому типу блока назначается одно из трёх действий, зафиксированное в `read_rules.yaml`:

| Действие | Что попадает | Пример |
|---|---|---|
| **skip** | Оглавление, колонтитулы, номера страниц, библиография, указатели | Не попадает в аудио вообще |
| **rewrite** | Схемы и цепочки: `chain`, `flow` | `A → B → C` → «А ведёт к Б, Б — к В». Переписанный текст лежит в карте рядом с исходным блоком, пишется человеком один раз |
| **read** | Абзацы, заголовки, `stack`, врезки | Читается как есть; `stack` — с паузой 500 мс между шагами |

Карта — человеческий артефакт того же класса, что `.acc.txt`: правится руками, лежит в git, переживает пересборку. Объём определяется подсчётом блоков по типам на шаге 1 (в предыдущей книге серии контрольные числа были: 2 chain, 11 flow, 7 stack — здесь считать заново).

Приложения, глоссарий и бонусные материалы решаются отдельно: часть из них в аудио не имеет смысла (перекрёстные ссылки, таблицы), часть читается.

### 5.2 Чанкинг

Цель 120–220 символов (1–2 предложения), жёсткий потолок 250, минимум ~40 — короче склеивать со следующим. Не рвать внутри кавычек и скобок, не заканчивать на предлоге, союзе или «не». Абзац — всегда граница. Заголовок главы — отдельный чанк с паузой 1500 мс.

Формат (`chNN.chunks.jsonl`, строка на чанк):
```json
{"id":"ch01-0001","ch":1,"n":1,"text":"…текст с ударениями…","pause_after_ms":350}
```

### 5.3 Синтез

- **Латенты референса считаются один раз.** У XTTS извлечение conditioning latents из wav — заметная доля времени на чанк. Считаются при первом запуске, сохраняются в `ref/<name>.latents.pt`, переиспользуются. Даёт скорость и стабильность тембра между главами.
- Хеш чанка: `sha1(текст + модель + seed + параметры генерации + хеш файла латентов)`. Смена референса инвалидирует кеш — это правильно.
- Воркеры — под `spawn`, число берётся из `.env`, потоки torch делятся между ними.

### 5.4 Сборка

- **Тримминг краёв.** XTTS оставляет хвостовую тишину неопределённой длины. Перед склейкой — обрезка тишины с обеих сторон по порогу (`silenceremove` / детектор по RMS), только потом вставка заданной паузы. Иначе значения пауз не соблюдаются и ритм плывёт.
- Паузы: 350 мс между предложениями, 900 в конце абзаца, 500 между шагами `stack`, 1500 после заголовка, 2000 в конце главы.
- Кроссфейд 20 мс на стыках — против щелчков.

### 5.5 Контроль качества

Порог: CER > 5% → переозвучка с другим seed, до 3 попыток, дальше в ручную очередь.

**Сравнение идёт не с `.acc.txt` напрямую.** Транскрипт ASR и исходный текст живут в разных нормализациях: в тексте ударения, «ё» и числа прописью после RUNorm, у whisper — цифры, без ударений, своя пунктуация. Прямое сравнение даст очередь переозвучки на половину книги.

Перед вычислением CER обе строки прогоняются через одну функцию сравнения: снять знаки ударения, `ё → е`, нижний регистр, убрать всю пунктуацию, привести числа к единому виду (либо оба прописью, либо оба цифрами), схлопнуть пробелы. Функция покрывается тестом слоя 1 на парах «текст / реалистичный транскрипт».

### 5.6 Мастеринг и контейнер

Звук: −19 LUFS, тру-пик −3 dB, highpass 80 Гц, 44.1 кГц.

Выход: главы в mp3 отдельно плюс единый `.m4b`. Метаданные `.m4b` заполняются из `config.yaml`, а не остаются пустыми: обложка (из PDF-сборки книги), автор, название, год, язык `rus`, жанр, названия глав с таймкодами. Для mp3 — ID3v2 с теми же полями плюс номер трека.

Если для финала выбран Chatterbox — проверить, переживает ли его вотермарк кодирование в mp3 128 kbps. Если ломается, это повод посмотреть и на то, что он делает со звуком.

## 6. Тестирование

Три слоя. Первые два — секунды, без моделей, гоняются в CI на обеих ОС.

**Слой 1 — логика и переносимость (pytest):** чанкер соблюдает диапазоны и границы; хеш меняется при смене seed/референса/латентов; арифметика пауз; нормализатор сравнения для CER на модельных парах; применение `read_rules.yaml` к блокам; loudnorm попадает в −19 LUFS; тримминг тишины даёт ожидаемую длительность; `open()` везде с `encoding="utf-8"` (greptest); нет `os.path.join` и склейки путей строками; нет обращений к `~/.cache`; `ffmpeg` ищется сначала в `bin/`.

**Слой 2 — имитация Windows на Mac:** подменённый `HOME` с проверкой, что туда ничего не записалось; принудительный `spawn` вместо `fork`; `HF_HUB_OFFLINE=1` — пайплайн обязан работать без сети; принудительный `--device cpu`; прерывание синтеза и перезапуск с кешем.

**Слой 3 — реальные модели (`RUN_SLOW=1`):** три чанка через XTTS → faster-whisper → CER < 5%, плюс замер RTF. Локально, не в CI.

**CI:** matrix `macos-latest` + `windows-latest` → `uv sync` (главная проверка переезда: резолвится ли lock на Windows), `doctor --no-models`, `pytest -m "not slow"`.

## 7. Процедура переезда Mac → Windows

1. На Mac: `uv sync --extra dev`, `./run.sh doctor`, `pytest`, `RUN_SLOW=1 pytest -m slow`, полный прогон одной главы в режиме `AUDIOBOOK_DEVICE=cpu` с прерыванием посередине.
2. `git push` — код, `text/`, `read_rules.yaml`, `config.yaml`. CI зелёный на обеих ОС.
3. На физический носитель: `models/`, `bin/ffmpeg.exe`, `ref/` (включая файл латентов), опционально `cache/`.
4. На Windows: `git clone`, скопировать папки, `cp .env.example .env`, `uv sync --extra dev`, `run.bat doctor`, `run.bat bench`.

**Критерий готовности к переносу:** CI зелёный + слой 3 прошёл + одна глава собрана на Mac на CPU + `doctor` знает про каждый скопированный артефакт.

Референс голоса и веса моделей в публичный репозиторий не кладутся.

## 8. Экономика времени

Бенчмарк меряет RTF (время синтеза / длительность аудио). Книга ≈ 7 часов = 25 200 секунд; время рендера ≈ RTF × 7 часов плюс ~20% на переозвучку брака.

**Решение принимается по `run.bat bench` на прод-машине.** Apple Silicon на CPU-инференсе ведёт себя иначе, чем Zen: замер на Mac показывает только то, что модуль работает и порядок величины. Мерить нужно при той же параллельности, что в проде — 4 воркера по 2 потока и 1 воркер на 8 потоков дают разный RTF на одном железе.

| RTF (на Ryzen) | Часов рендера | Решение |
|---|---|---|
| < 4 | 30–40 | Локально, ночными батчами за неделю |
| 4–8 | 50–80 | На грани: одна глава за ночь |
| > 8 | 100+ | Аренда GPU |

**Запасной вариант.** Пайплайн не меняется ни строкой: разработка и отладка локально на трёх абзацах, полный рендер — на арендованной GPU-машине за вечер. Из российских площадок — immers.cloud, Selectel; это снимает санкционный риск. Покупка б/у RTX 3060 12 ГБ окупается только если озвучка станет регулярной задачей.

## 9. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Конфликт зависимостей `coqui-tts` / `ruaccent` по transformers | Высокая | Разрулить на Mac при первом `uv sync`, зафиксировать в lock |
| Клон «плывёт» на длинных главах: интонация уплощается, вопросы звучат утверждениями | Высокая | Слепой тест на 8–10 слушателях из аудитории; гибридный сценарий |
| Ложные срабатывания CER из-за разных нормализаций | Высокая | Общий нормализатор сравнения + тест слоя 1 на реалистичных парах |
| Невербальные блоки прочитаны буквально | Высокая | `read_rules.yaml` + прослушивание первой главы целиком до массового рендера |
| RTF на CPU выше ожидаемого | Средняя | Бенчмарк на прод-машине до написания остальных модулей; аренда GPU как план Б |
| Ошибки ударений в омографах | Средняя | Вычитка `chNN.acc.txt` до синтеза + словарь исключений |
| Веса не переехали, Windows лезет в HuggingFace | Средняя | `HF_HUB_OFFLINE=1` + `doctor` проверяет наличие каждого файла |
| Вотермарк Chatterbox ломается при кодировании в mp3 | Низкая | Проверить на пилотной главе при выборе модели |
| Лицензия XTTS-v2 блокирует продажу | Определённая | Пилот на XTTS, финал на Chatterbox/Qwen3-TTS |

**Рекомендуемый сценарий — гибрид:** автор живьём читает предисловие и первую главу (те 20 минут, где формируется доверие), остальное синтез. Снимает главный риск дёшево.

## Приложение: требования к референсу

Не самый выразительный фрагмент, а самый чистый и ровный: 10–20 секунд, mono, 24 кГц, нейтральная читательская манера, без музыки, эха и придыхания в микрофон. Нарезать 5–7 кандидатов, синтезировать одним и тем же абзацем, выбрать победителя на слух — разброс между референсами обычно больше, чем между моделями.

Победитель кладётся в `ref/`, рядом сохраняются его латенты. Менять референс после начала массового рендера нельзя — кеш обнулится и тембр разъедется между уже готовыми и новыми главами.

## Приложение: открытые вопросы

- Объём рукописи в знаках — для точной оценки времени рендера.
- Продаётся ли аудиоверсия отдельно или идёт бонусом — определяет, обязателен ли переход с XTTS на коммерческую лицензию.
- Есть ли готовая студийная запись голоса автора.
- Письменное согласие автора на клонирование — получено или нет.
- Какие приложения, глоссарий и бонусные материалы попадают в аудио.
- Тестовые фразы в `bench.py` — плейсхолдеры, написанные в стилистике книги, но **не цитаты**. Перед использованием заменить на реальные предложения из рукописи.
