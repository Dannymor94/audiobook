# T15 — инвентарь ударений

> **Итерация 3. Архитектурное решение принято 2026-11-09.** Этот раздел заменяет противоречащие ему детали ранней реализации. Исходные ограничения проекта остаются в силе. До PASS Codex Sol статус остаётся `review`, T16 заблокирована. Изменения делать в отдельном worktree `task/T15`, не сливать самостоятельно.

## Зачем

Ударения нельзя надёжно проверить автоматически по аудио (детектор фонем совпал с ухом в 1 из 6 случаев, G18). Нужен конечный детерминированный список словоформ риска для проверки на слух. Базовый замер проекта: 75 722 слова, 10 305 словоформ; топ-300 форм = 55% текста, топ-1000 = 72%.

## Исходный функциональный контракт (с учётом итерации 3)

Подкоманда `stress-inventory` (`src/audiobook/stress_inventory.py`): **только текст**, без моделей синтеза, без сети и новых зависимостей. Основной текстовый источник для проверки согласованности — `text/*.norm.txt`; **источником конкретных вхождений** становится текст из `out/sections/<section>/manifest.jsonl` до подстановок `pronounce.yaml`.

- **Омографы:** из офлайн-словаря RUAccent в `models/`, в отдельном отчёте по каждому вхождению: секция, точный `chunk_id`, контекст, вариант RUAccent или причина `unresolved`.
- **Список риска:** топ-N (параметр `stress.top_n`, по умолчанию 300), все омографы, кандидаты в имена, слова из `pronounce.yaml` и `stress_watch.yaml`, за вычетом `text/stress_verified.yaml`.
- **Частоты и покрытие:** детерминированная сортировка; число уникальных словоформ и их вхождений по каждой причине и по объединению.
- **Контекст:** фрагмент не длиннее 80 символов, содержащий целиком именно рассматриваемое вхождение. Если форма длиннее 80 символов — ошибка и отказ.
- **Формат:** старые колонки и порядок сохраняются; новые `status`, `reason` — только в конце. Первая колонка `risk.tsv` и нормализация не меняются.

## Итерация 3 — обязательная подготовительная проверка (STOP-GATE 0)

**До любых правок логики агент должен:**

1. Прочитать `CLAUDE.md`, `AGENTS.md`, `tasks/README.md`, эту задачу. Проверить текущую ветку/worktree и известную базу.
2. Показать фактическую структуру **одной строки** `manifest.jsonl` (названия полей и типы; не раскрывать текст книги в отчёте; допускается `head -1` локально), выяснить, какое поле содержит текст чанка **до** подстановок `pronounce.yaml`.
3. Без изменения файлов проекта выполнить пробную проверку: склеить тексты чанков по правилам ниже, сравнить кириллические токены с соответствующим `norm.txt` (`lower`, `ё→е`). Сообщить количество токенов обеих сторон, PASS/FAIL, первое различие, название использованного поля.
4. Проверить наличие и формат словаря RUAccent.

**Если ни одно поле манифеста не даёт точного совпадения токенов — STOP: `blocked`, сохранить диагностику и вернуть вопрос архитектору. Не пытаться молча переопределять текстовый контракт и не приступать к логике итерации 3.**

## 1. Источник вхождений и точные chunk_id

- Для каждой секции склеить тексты чанков из манифеста в одну строку; попутно построить интервалы `(start, end, chunk_id)`.
- На границе исходного абзаца ставить `\n\n`, иначе — пробел. Использовать установленный в STOP-GATE 0 текст до произносительных подстановок.
- Искать словоформы только в полученной строке. Через `bisect` по смещению начала формы получать соответствующий `chunk_id`; подтверждать, что форма попадает в ожидаемый диапазон. Формы на границах обрабатывать без неверных ID.
- Обязательная проверка **на каждой секции**: последовательность кириллических токенов склейки после `lower`, `ё→е` в точности равна последовательности `norm.txt`. Расхождение: ненулевой exit code, первое несовпадение с диагностикой, без публикации новых отчётов.
- Удалить старый алгоритм «слово → список chunk_id по порядку». `chunk_id = ?` в нормальном успешном запуске недопустим.
- Chunker, манифесты, хеши и кеш не менять.

## 2. RUAccent: сопоставление по позиции

- Одна функция определения границ предложений, используемая и RUAccent, и классификатором имён.
- RUAccent вызывается один раз на каждое предложение. Для входа и выхода использовать одинаковый regex токенизации; в выходе убрать `+`, привести обе стороны к `lower` и `ё→е`.
- Если токены по порядку совпадают — сопоставлять по индексу.
- Если не совпадают — применить `difflib.SequenceMatcher` из stdlib; принимать только блоки `equal`, остальное маркировать `unresolved / tokenization_mismatch`.
- Если у омографа в выходе отсутствует `+` — `unresolved / no_stress`. Никаких ударений по умолчанию.
- Отдельно держать обнаружение омографа по словарю и извлечение контекстного варианта RUAccent.
- Для каждого повторного вхождения отдельная позиция, контекст и значение/причина.

## 3. Ошибки и неопределённость

**Ошибка: `rc != 0`, публикации нет:** нет словаря, неверная структура/типы, исключение инициализации RUAccent, исключение обработки любого предложения, несовпадение токенов манифеста и `norm.txt`, словоформа длиннее 80 символов. Нельзя скрывать исключения через `except Exception: ...` с продолжением успешного отчёта.

**Допустимая неопределённость: `rc = 0`, учитывается в summary:** `unresolved / no_stress` и `unresolved / tokenization_mismatch`. Не подставлять приблизительное ударение.

3. До публикации валидировать число строк относительно summary и заголовки TSV.

Изменения потребителей организовать отдельно по согласованному контракту, без внесения несанкционированных правок в чужие ветки.

## 5. Имена

Началом предложения считается начало секции/абзаца либо позиция после `. ! ? …` с пропуском пробелов и открывающих кавычек/скобок/тире (`«`, `"`, `“`, `(`, `—`). Точка после одиночной заглавной буквы (инициал) не создаёт новую границу. Сокращения уже раскрыты RUNorm.

Кандидат `name`:
- заглавное слово **не** в начале предложения; **или**
- заглавное слово в начале предложения, **если** эта форма нигде не встречается со строчной и хотя бы раз встречается заглавной **внутри** предложения.

Использовать ту же функцию границ предложений, что и при разметке RUAccent. `name` — эвристический признак риска, не доказательство, что слово является именем.

## 6. Контекст

Окно строится от точного диапазона `[start, end)` словоформы. Длина ≤80 символов, словоформа целиком. Окно может пересекать границу чанка, но `chunk_id` вычисляется по позиции **самой формы**, а не началу контекста. Если длина формы >80 — `rc != 0`.

## 8. Тесты (только синтетические данные)

1. Одинаковое слово дважды в предложении с разными ударениями: отдельные контекст и вариант для каждого вхождения.
2. Повторы в разных абзацах/чанках → точные `chunk_id`.
3. Несовпадение токенов manifest vs `norm.txt` → ошибка с первым различающимся токеном.
4. RUAccent изменяет токенизацию → `unresolved` только в неравных блоках, неизменённые токены сопоставляются.
5. Нет словаря; неверная структура; исключение init; исключение на предложении → отказ, старый `inventory/` сохранён.
6. Ошибка между записью файлов → предыдущий согласованный `inventory/` не повреждён; тест восстановления после прерванной замены.
7. Обычное заглавное слово в начале 2-го предложения ≠ `name`; заглавное внутри = `name`; инициалы не создают ложную границу.
8. Длинная форма у правой границы полностью в контексте, `len≤80`; форма >80 → отказ.
9. Существующий тест детерминизма `PYTHONHASHSEED=1/2/3` сохранить без изменений.
10. Состав хешей чанков и `impact` не изменился.
